# Регулярная проверка производительности Bitrix

Раз в месяц коллега собирает 10-минутный срез боевого трафика в таблицы perfmon на etalon, а воркфлоу YouTrack 1-го числа заводит
в проекте bxkor тикет «Выполнить регулярную проверку Битрикс». Наша часть — найти, что тормозит, доказать причину данными среза
и кодом и оформить задачи так, чтобы исполнителю не пришлось анализировать заново. Регламент — wiki
[«Анализ производительности приложения»](https://wiki.example.com/Анализ_производительности_приложения), раздел «Производительность
системы»; пороги — хиты с более чем 300 запросами к БД и дольше 1 с.

## Данные клиентов — правило

В срезе боевой трафик: в `b_perf_sql.SQL_TEXT` и `b_perf_hit.REQUEST_URI` лежат логины и email, телефоны, IP, ID пользователей
и заказов, поисковые фразы, хеши сессий. YouTrack читают подрядчики, артефакты и документы живут на внешнем сервисе, персональные
данные защищены 152-ФЗ. Поэтому:

1. **Значения не покидают БД среза.** Всё из БД — только через скрипты скилла: они маскируют вывод ещё в контейнере (`PerfMask`).
   Литералы SQL → `'X'` (кроме дат и коротких кодов вида `'Y'`), URI — без значений параметров, кроме технических (`PAGEN_*`,
   `SECTION`, `BRAND`…), числа от 4 цифр в путях ЛК и деска → `N`. Если запрос касается не только perfmon и служебных таблиц,
   строки и ID показываются псевдонимами `‹id:abcdef›` (одинаковые значения видны одинаковыми, восстановить нельзя). Режима без
   маски нет.
2. **Свои запросы и скрипты** — через `perf_sql.php`, а в одноразовом PHP — `PerfMask::row()` или `::text()` на каждой печатаемой
   строке. Из таблиц с данными людей — только агрегаты, `EXPLAIN`, `SHOW INDEX`, число строк. Нельзя `EXPLAIN FORMAT=JSON` (в нём
   значения условий), сырые выгрузки в файлы, печать `SQL_TEXT`/`REQUEST_URI` в обход маски.
3. **Наружу — только шаблоны, метрики и указатели.** В тикет, комментарий, артефакт, документ, презентацию, сообщение идут страницы
   без значений параметров, нормализованный SQL, числа, планы, `file:line`, номера тикетов и `HIT_ID` — указатель в срез: номера
   хитов короткие и сбрасываются с каждым срезом, коллега с доступом найдёт пример сам. `sql_id` — только для своей работы
   (`perf_explain.php`): он семизначный, проверка его не пропустит. Нельзя: реальные URL с параметрами, ID пользователей, заказов,
   КП и клиентов, email, телефоны, ФИО, названия компаний-клиентов, IP (хост БД пишется словом «etalon»), скриншоты страниц с данными клиентов.
4. **Перед любой отправкой — проверка точного текста:** `php .claude/skills/perf-check/scripts/pii_check.php <файлы>`.
   Генераторы `yt/drafts.php` и `yt/comment.php` проверяют сами и при находке ничего не создают. Находку переписать, а не обходить,
   ложное срабатывание тоже: число — с пробелами по разрядам, хост — «etalon», пример — через `HIT_ID`.
5. **Если данные уже ушли** (нашлось в отправленном) — остановиться, сказать пользователю, что и где, и предложить удалить или
   отредактировать. Дальше не отправлять.
6. **Субагенту** передать этот раздел дословно — скилла у него нет.

Маскирование покрыто тестом на синтетических данных: `php .claude/skills/perf-check/scripts/test/mask_test.php`.

## Что нужно до начала

- Контейнер `php-fpm` (`docker ps`). Хост БД среза — обязательный `-e PERF_DB_HOST=…` (хост etalon).
  Без него скрипт откажется, а не уйдёт молча на дефолтную тестовую базу со старым срезом.
- Номер текущего тикета bxkor и окно среза — из комментария коллеги в нём. Если пользователь не назвал номер — найти поиском (шаг 5) или спросить.
- Playwright MCP (`mcp__playwright__*`) с постоянным профилем, залогиненным в YouTrack. При редиректе на страницу входа Hub —
  попросить пользователя войти самому; пароли не вводить.

Команды ниже сокращены: `perf <скрипт> …` — функция zsh (переменная с командой в zsh не разбивается на слова). `XDEBUG_MODE=off`
убирает шум Xdebug; stdout — результат (его можно писать в файл), stderr — баннер среза.

```bash
perf() { local s=$1; shift; docker exec -e XDEBUG_MODE=off -e PERF_DB_HOST=<PERF_DB_HOST> php-fpm php /var/www/project/.claude/skills/perf-check/scripts/$s "$@"; }
```

## Цикл

### 1. Папка среза и опознание

Папка `.claude/tasks/perf-YYYY-MM-DD/` (дата среза) с `raw/` и `tickets/`; `.claude/tasks/` должна быть в `.git/info/exclude`
(проверить, при отсутствии — добавить строку `/.claude/tasks/`). Затем:

```bash
perf perf_overview.php /var/www/project/.claude/tasks/perf-YYYY-MM-DD/raw/overview.json > .claude/tasks/perf-YYYY-MM-DD/raw/overview.md
```

Сверить баннер `[срез … – …, N хитов]` с окном из bxkor. Если окно прошлого месяца — нового среза в БД нет: остановиться и спросить.
`overview.md` — готовые таблицы регламента: пороги по страницам, страницы по шаблону пути, худшие хиты и вызовы компонентов, фазы,
самые долгие запросы, оценка `TOTAL_MARK`.

### 2. Сравнение с прошлым срезом

`php .claude/skills/perf-check/scripts/perf_compare.php <прошлый>/raw/overview.json <текущий>/raw/overview.json` — дельты итогов,
порогов, страниц и компонентов, **(новое)** у появившихся. До 11.2026 JSON нет — сравнивать с README прошлого среза.
Регрессии и новое в топе — первые кандидаты в тикеты.

### 3. Тяжёлые запросы

Полный проход по `b_perf_sql` занимает минуты, поэтому запускать отвязанно, с логом в файл (фоновый пайплайн сессии теряет вывод):

```bash
docker exec -d -e XDEBUG_MODE=off -e PERF_DB_HOST=<PERF_DB_HOST> php-fpm sh -c 'php /var/www/project/.claude/skills/perf-check/scripts/perf_sql_patterns.php 0 60 > /var/www/project/.claude/tasks/perf-YYYY-MM-DD/raw/sql_patterns_all.txt 2>&1'
```

Пока идёт полный проход, быстрый срез — `perf perf_sql_patterns.php 0.05 30`. Шаблон даёт Σ времени, число выполнений, хитов,
компоненты и `sample_hit`.

### 4. Разбор каждой находки до причины

- Повторы внутри хита (N+1): `perf perf_hit_patterns.php <hit_id>`.
- План и контрольный прогон: `perf perf_explain.php <sql_id,…>` (`sql_id` — из overview или `perf_sql.php`); выполняются только SELECT.
- Свои выборки: `perf perf_sql.php "SELECT …"` (только чтение, вывод маскирован; рецепты — `references/perfmon.md`).
- Место в коде: backtrace в perfmon выключен, поэтому искать grep-ом по таблице, ORM-алиасу (`api_ship_terminal`, `commercial_offers`)
  и полям, затем идти по вызовам до компонента или пролога. Каждое утверждение — с `file:line`.
- Гипотезу проверять измерением: на etalon (скрипт в контейнере, печать только агрегатов — время, число SQL, память) или на локальном стенде.

Находка готова, когда есть цифры среза, механизм с `file:line`, «что делать», критерий приёмки в терминах следующего среза и оценка
эффекта. Независимые находки можно разбирать параллельно субагентами — с правилом о данных клиентов в задании.

### 5. Похожие тикеты в YouTrack

Через Playwright MCP, подробно — `references/youtrack.md`:
1. `browser_run_code_unsafe` с `filename=.claude/skills/perf-check/scripts/yt/auth.js` — токен и помощники на `window`.
2. `browser_evaluate` с `filename=.claude/tasks/perf-…/tickets/search.json` и функцией
   `() => window.__ytSearch(['project: mg "из регулярной проверки Bitrix"', 'project: mg <таблица/страница/компонент>', …])`.
   Простые запросы, по одному ключу на находку. Плюс `__ytIssues([...])` по тикетам из реестра в `references/perfmon.md`.
3. Решение по каждой находке: **новый тикет**; **комментарий** в открытый тикет на ту же тему (дубль не заводить); **ничего** —
   уже закрыт с релизом, и в срезе эффект виден. Решения — в README среза.

### 6. Тексты и черновики

1. `README.md` и `NN-<тема>.md` по шаблонам `references/templates.md`. Каждый `NN-*.md` — это описание тикета.
2. `tickets/tickets.json` — заголовок с маркером «(из регулярной проверки Bitrix)», сервис, связи (bxkor и смежные), описание.
3. `php .claude/skills/perf-check/scripts/yt/drafts.php .claude/tasks/perf-…/tickets/tickets.json` — проверка (данные клиентов,
   маркер, сервис, ровно один bxkor, разделы) и `fill_NN.js`. При находке файлы не пишутся — исправить и повторить.
4. Для каждого тикета: `browser_tabs new` с `https://youtrack.example.com/newIssue?project=mg` → подождать 6 с → `browser_run_code_unsafe`
   с `filename=…/fill_NN.js`. Черновик сохраняется сам (`draftId`), «Создать» не нажимается. Затем `yt/verify.js` по всем вкладкам.
5. Показать пользователю таблицу: черновик, заголовок, сервис, связи, «похожие задачи» из формы. Если YouTrack нашёл похожую
   открытую задачу — обсудить до создания.

### 7. Создание и комментарии — только по явной команде

Создание задач и комментарии публикуют текст для всей компании, поэтому только после явного «создавай» или «публикуй» пользователя:
- `browser_run_code_unsafe` с `filename=…/tickets/create_all.js` — создаёт задачи из всех открытых черновиков, прошедших сверку.
- Итог в bxkor и комментарии в открытые тикеты: `php .claude/skills/perf-check/scripts/yt/comment.php <id> <текст.md> <out.js>`
  (проверка внутри), затем `browser_run_code_unsafe` с `filename=<out.js>`. Дубль не отправится: JS сверяет начало текста.

### 8. Итог

Таблица «разбор → тикет → сервис» в README; project-заметка в памяти о срезе (что заведено, что осталось, кандидаты на следующий
срез); в ответе пользователю — ссылки на тикеты, черновики и то, что ждёт его решения.
